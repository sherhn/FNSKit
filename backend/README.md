# Backend ФНСКит

Стек состоит из двух контейнеров:

- `nginx` (`:80`) — единственный публичный сервис: раздаёт статику сайта и проксирует API;
- `processor` (`:8080`) — принимает файлы и собирает TIFF либо PDF.

Базы данных, ключей, оплаты и отправки писем нет: сервис бесплатный и ничего не
хранит. Файлы живут во временной папке только на время обработки.

## Запуск

```bash
docker network create dokploy-network   # один раз, если запускаете не в Dokploy
docker compose --env-file .env -f backend/docker-compose.yml up --build -d
```

Сайт — <http://localhost:8082>, документация процессора —
<http://localhost:8080/docs>.

Публичный `POST /api/processor/v1/tiff` принимает профиль, файлы и отметку о
согласии на обработку ПДн (`personal_data_consent` и `consent_version`, см.
[processor/README.md](processor/README.md#запрос)). Поле `output_format`
принимает `tiff` (по умолчанию) или `pdf`. PDF разрешён только для профиля
`vat`: это многостраничный image-only PDF, собранный заново из страниц в
300 DPI, 8-битном сером цвете и JPEG-качестве 92. Ссылки, JavaScript, формы,
вложения и метаданные исходников в результат не переносятся. PDF пишется
потоком, страница за страницей, поэтому его размер ограничен не памятью, а
только дисковым пределом запроса (`MAX_RENDERED_MEGABYTES`); число страниц и
размеры страницы используют общие лимиты процессора.

Ручка анонимная, поэтому её защищают лимиты в процессоре и в nginx: частота
запросов с одного IP, число одновременных загрузок, общий предел принятых
файлов на диске и очередь обработки (подробности —
[processor/README.md](processor/README.md#защита-анонимной-ручки)).

Порты `8080` и `8082` слушаются только на `127.0.0.1`.

## Публикация наружу

Наружу смотрит только `nginx`. Всё для него лежит в каталоге `site/` рядом с
`backend/`: страницы сайта, `Dockerfile` и `nginx.conf`. Контекст сборки — сам
`site/`, поэтому в образ физически не может попасть ни `.env`, ни исходники
бэкенда. Статика раздаётся по адресам без `.html`: `/privacy` вместо
`/privacy.html` (старые адреса отвечают `301`). API проксируется на тот же домен:

| Публичный адрес | Куда идёт |
| --- | --- |
| `/api/processor/...` | `processor:8080` |
| `/healthz` | ответ самого nginx |

Один origin на сайт и API — поэтому CORS в продакшене не участвует, а
`site/js/config.js` подставляет фронтенду относительный адрес. `/docs`,
`/redoc`, `/openapi.json` и `/health` наружу не отдаются: nginx отвечает на них
`404`.

TLS, сертификаты и редирект с `http` делает Traefik из Dokploy — в панели домен
привязывается к сервису `nginx`, порт `80`. Поэтому контейнер подключён к
внешней сети `dokploy-network`.

Правки статики и `nginx.conf` попадают в образ на сборке, поэтому после них
нужна пересборка образа `nginx`: локально `docker compose up --build -d nginx`,
в продакшене — новый образ в реестре и redeploy.

## Деплой

На сервере используется `docker-compose.prod.yml`: он отличается от основного
файла только тем, что берёт готовые образы из `ghcr.io/sherhn/fnskit-*`
вместо сборки. Собирать на машине с 400 МБ ОЗУ дорого — сборка съедает больше,
чем весь работающий стек.

```bash
export IMAGE_TAG=$(git rev-parse --short HEAD)
docker build -t ghcr.io/sherhn/fnskit-nginx:$IMAGE_TAG ../site
docker build -t ghcr.io/sherhn/fnskit-processor:$IMAGE_TAG ./processor
for name in nginx processor; do
  docker tag ghcr.io/sherhn/fnskit-$name:$IMAGE_TAG ghcr.io/sherhn/fnskit-$name:latest
  docker push ghcr.io/sherhn/fnskit-$name:$IMAGE_TAG
  docker push ghcr.io/sherhn/fnskit-$name:latest
done
```

В продакшене ни один порт на хост не публикуется: сервер общий с другими
проектами Dokploy, и `8080` или `8082` там могут быть уже заняты. Наружу
смотрит только `nginx` через Traefik, `processor` доступен по имени внутри сети
compose, а для отладки на сервере есть `docker exec`.

Настройки в продакшене живут во вкладке Environment в панели: Dokploy пишет их
в `.env` рядом с compose-файлом, то есть в `backend/.env`, откуда его и читает
`processor`. Поэтому в prod-файле путь `.env`, а не `../.env`, как в
локальном. Набор переменных — из `.env.example`, плюс `IMAGE_TAG`. Секретов
среди них нет.

Дальше в Dokploy — redeploy. Тег берётся из переменной `IMAGE_TAG`
(по умолчанию `latest`): чтобы откатиться, достаточно указать в панели тег
нужного коммита, пересобирать ничего не нужно.

Пакеты в ghcr создаются приватными, поэтому либо сделайте их публичными, либо
добавьте в Dokploy реестр с токеном, у которого есть право `read:packages`.

## Память

Весь стек рассчитан на 400 МБ. Значения ниже измерены, а не прикинуты:
`anon` из cgroup, то есть настоящая нужда без дискового кеша.

| Контейнер | В покое | Худший случай | Потолок |
| --- | --- | --- | --- |
| `processor` | 64 МБ | 211 МБ — страница на пределе 50 Мпикс | 320 МБ |
| `nginx` | 12 МБ | 24 МБ | 48 МБ |
| **Итого** | **76 МБ** | **235 МБ** | 368 МБ |

Потолок — предохранитель на случай сбоя, а не резервирование: поставить его
впритык нельзя — при превышении ядро убивает контейнер целиком, вместе с
чужими запросами.

Что определяет пик обработки: `MAX_PAGE_MEGAPIXELS` (около 115 МБ плюс
1,9 МБ на мегапиксель предела — в памяти только серая страница и её
чёрно-белая версия) и `MAX_CONCURRENT_JOBS` (каждая параллельная задача
добавляет полный пик). Оба поднимать только вместе с `mem_limit` процессора.
Рабочие файлы в памяти не лежат — для них у процессора дисковый том. Предел
не держит картинки внутри страницы PDF, которые декодирует MuPDF, поэтому
страница, где они не помещаются в память, рисуется полосами, а если не
помещается и так (JPEG 2000 на высоком разрешении), получает отказ: цветной скан
600 DPI в JPEG, вложенный в PDF, даёт пик 170-182 МБ вместо 369-446 МБ. Число
страниц память не держит.
